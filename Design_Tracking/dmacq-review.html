dMACQ DMS 7.0 review and the in-house build it implies

What the vendor product does, where it falls short, and what a Chandak Group document management application needs to match and improve on it.

Source: 8 uploaded dMACQ documents (Admin Guide 148 pp, feature deck, tech notes) · Reviewed 7 Oct 2026

Summary

  • dMACQ is a metadata-driven document repository, not a workflow engine. Its whole design rests on five linked objects: workspaces (“Deal Rooms”), a folder tree (“Categories”), document types (“Doc Sets”), free-entry fields (“Index Groups”) and master-data lookup tables (“Index Masters”).
  • Its strongest ideas are worth copying: per-folder metadata schemas, tagging documents against master records (employee, vendor, PO) imported from ERP/HRMS, a five-layer permission model, and bulk indexing from filenames, folder trees and Excel.
  • The “workflow” is a single approve/reject step per folder. The docs describe no version history, no audit trail, no multi-step routing and no retention rules. Those are the clearest places an in-house build can do better.
  • Several limits are design debt we should not reproduce: globally unique filenames, 26 banned filename characters, search limited to one folder, irreversible data loss when a field is deleted or a document is moved, and OS cron jobs plus fragile Excel templates for every bulk operation.
  • A practical MVP covers workspaces, folders, document types, custom fields, master tables, permissions, upload with indexing, a browser viewer, field search and QC approval, with versioning and audit logging built in from day one. The roadmap below phases the rest.

How dMACQ is built

Everything hangs off the folder. An administrator links each folder to the document types it may hold and the field sets its documents carry. Upload, search columns and filters are all driven by those links.

Security model

A user sees and does something only when every layer allows it. This is the part of dMACQ most worth reproducing faithfully, because users will expect the same behaviour.

  1. 1
    Role (group) functional rightsPer module: View, Create, Modify, Delete, Purge, Export. Controls which menus and buttons appear. Global across workspaces. Built-in groups: Super Administrators, Deal Managers, QC Approvers, Users. New groups start with everything denied; rights can be copied from another group. §4–5
  2. 2
    Workspace membershipA user enters only the deal rooms assigned to them. §3, §6.5
  3. 3
    Folder accessVisible or hidden per user or group. A hidden folder means no upload, view, search, download or print inside it. §8
  4. 4
    Document-type permissions per groupAdd, View, Print, Edit (metadata), Delete, Download, Mail, and Private View (only the uploader sees it, for payslips, medical records and similar). §10
  5. 5
    Field visibility per groupEach custom field and master field can be shown in lists and/or offered in search, per group. §13, §15.1
  6. 6
    Master table rightsPer user or group: create tables; view, modify, delete or export each table; add, edit or delete its rows; view its reports. §15.2

Account controls alongside: local or Active Directory login, optional two-factor and SSO, password policy (8–15 chars, mixed case, digit, symbol, expiry), inactive status, access start and end dates, one live session per username, named vs concurrent licences.

Limits to fix in-house

Items marked “not described” are absent from all eight documents; dMACQ may offer them elsewhere, but we should not assume so.

Not described Version history

No check-in/out, versions or replace-file action appear anywhere. Every serious DMS needs this. Build it in from day one.

Not described Audit trail

No record of who viewed, downloaded, edited or deleted what. Needed for compliance and for trust in Private View documents.

Thin Workflow

One approve/reject gate per folder. No multi-step routing, assignees, due dates or reminders. A configurable approval chain is a natural Phase 3 item.

§24

Filename rules

Duplicate filenames are rejected and 26 characters are banned because of the firewall. Store files by internal ID and keep the original name as plain metadata.

§17.2 · Recommendations

Search scope

Folder search ignores sub-folders, and unindexed documents are searchable only by name, type and date. Default to “this folder and below”.

§23.3

Silent data loss

Deleting a field or field group erases its values permanently; moving a document to a folder without the same fields drops its values. Use soft deletes and keep values on move.

§12.4, 12.8, 22.4

Fragile Excel templates

Every bulk path depends on a template that fails if any cell is edited. Accept plain CSV/XLSX with header matching and a row-level error report.

§6.1.3, 14.10.2, 22.3

Ops burden

Conversion, OCR, imports and indexing are OS cron jobs; server paths are typed with doubled backslashes. Use a managed job queue with a status screen.

§14.10.2.2, 18.2, 25.2

Private saved views

Views and searches belong to one user and cannot be renamed. Allow sharing with a group and renaming.

§21.2, 23.3.1

Rigid one-to-ones

One type per document, one unique field per master table, each type in only one set per workspace. Keep these as defaults but avoid hard-coding them.

§9, 14.6, 17

View-only viewer

No annotations, redaction, watermarking or print-with-watermark. Download/print control exists but the content leaves unmarked.

§18.2

Single session

One login per username at a time, tied to licence counting. Not needed in-house; allow multiple sessions with session management.

Suggested stack

dMACQ runs PHP on Apache with MySQL or SQL Server and plain file-system storage, on Ubuntu or Windows Server. The default below keeps it on-premises and Linux-based, but uses current components. It is a recommendation to confirm with whoever will maintain the app.

Phased roadmap

MVP: replace day-to-day use

  • Workspaces, folder tree, document types, custom fields, master tables (manual + Excel import with error report), folder linking
  • Users, groups, AD login, 2FA, the six permission layers including Private View
  • Upload with no / single / per-file indexing, inline new master row, upload from a master row
  • Viewer for PDF, Office, images and text; download and download-with-metadata; recycle bin
  • Folder field search (including sub-folders), column picker, status filters
  • QC approval per folder with comments and bulk approve
  • Version history and audit log from the first release

Phase 2: power-user features

  • Global search with operators, content search, OCR, shareable saved views and searches
  • Bulk actions: file in more folders, move (keeping values), Excel indexing, bulk download, list export, email links
  • Document links, dashboard with favourites and due-date report
  • Filename auto-indexing and auto-rename patterns

Phase 3: automation and integration

  • Hot-folder and folder-tree bulk import, scheduled master imports from ERP/HRMS, re-indexing
  • Multi-step approval workflows with assignees, due dates and reminders
  • Retention and expiry rules, watermarking, CAD and media preview, public REST API
  • Migration tool for existing dMACQ content and metadata, if Chandak Group runs dMACQ today

Open questions

These change scope and design. Answers in the project thread are enough.

  1. Does Chandak Group run dMACQ today? If so, roughly how many documents and how much storage would need migrating with their metadata?
  2. Which companies or divisions become workspaces, and roughly how many users in each?
  3. Hosting: an on-premises server (the default assumed here) or a cloud provider?
  4. Login: Microsoft Active Directory / Entra ID, Google Workspace, or local accounts only?
  5. Masters to import: which systems hold employee, vendor and PO data (ERP, HRMS, Tally, SAP)?
  6. Beyond dMACQ: which of version history, multi-step approvals, e-signature, retention rules and mobile access are must-haves?
  7. Tech stack: does the IT team have a preferred language or framework to maintain?
